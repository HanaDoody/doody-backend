## 목적과 판정 원칙

기존 서비스의 반복 검증을 자동화하기 위한 기준 문서다. 아래의 '현재 동작'은 소스에서 관찰한 사실이며, 제품 요구사항이나 테스트 실행으로 검증된 결과와 동일하지 않다. 정책이 불분명한 항목은 정답으로 확정해 자동 테스트에 넣지 않는다.

## 정책 결정이 필요한 항목

이 항목은 코드 검토에서 나온 질문이다. 실제 결함으로 확정하거나 자동으로 서비스 코드를 수정하지 않는다.

| ID | 코드에서 관찰한 점 | 결정할 사항 |
| --- | --- | --- |
| P01 | 완료된 최신 로그는 재사용하지 않고 새 로그를 만들 수 있음 | 같은 미션 반복 완료 허용 여부, 일/회차 기준, 중복 보상 정책 |
| P02 | AI complete 결과의 completed 플래그를 조건으로 삼지 않고 로그 완료와 보상 처리를 진행 | completed=false일 때 처리 중단 여부 |
| P03 | 수집 시 위경도의 null만 검사 | 위도·경도 범위, 음수/비정상 radius 처리 |
| P04 | AI 미연결 시에도 수집 fallback에서 보상 30과 고정 ARI 사용 | 운영 환경의 장애 시 보상·상태 정책 |
| P05 | 템플릿 조회 실패 시 저장 템플릿만 대체하고 응답에는 AI의 두디를 사용 | 저장 데이터와 응답 ID를 일치시켜야 하는지 |
| P06 | 수집품 중복 검사와 달리 포인트 적립에는 중복 출처 검사가 없음 | 재시도·동시 요청에 대한 멱등성 보장 범위 |

## 검증 계층

1. 서비스 단위 검증: Repository와 AI 클라이언트를 대역으로 주입한다. AWS, DB, AI 서버 없이 분기·저장 요청을 검증한다. 트랜잭션 및 실제 DB 동작을 증명하지는 않는다.
2. HTTP 계층 검증: 요청 역직렬화, 공통 오류 처리, 상태 코드와 응답 필드를 검증한다. 서비스 예외만 보고 실제 HTTP 응답 형식을 단정하지 않는다.
3. DB 연동 검증: 격리한 로컬 PostgreSQL에서 매핑, 제약, 롤백을 확인한다. 기존 운영 DB에 접속하지 않는다.
4. 결함 탐지 평가: 별도 코드 복사본에서 조건을 변경하고 새 테스트가 실패하는지 확인한다. 정상 코드에서도 통과하는지 함께 확인한다.

## 에이전트 평가 계획

| 평가 사례 | 주입할 변경 | 기대 관찰 |
| --- | --- | --- |
| E01 | 포인트의 0 이하 거절 조건 제거 | 잘못된 적립을 탐지 |
| E02 | 기존 두디 보유 여부 확인 제거 | 중복 수집 저장을 탐지 |
| E03 | 수집 거리 제한 조건 반전/제거 | 먼 위치의 수집 허용을 탐지 |
| E04 | 미션의 축 검증 제거 | 다른 축 미션 완료 처리를 탐지 |
| E05 | 변경하지 않은 기준 코드 | 잘못된 경고 및 테스트 실패 여부 확인 |

평가 기록에는 시도한 사례 수, 정상 코드에서 통과한 테스트, 탐지한 변경, 누락, 잘못 생성한 테스트와 수정 횟수를 남긴다. 이 표는 계획이며, 아직 실행된 성과가 아니다. 소수의 수동 변경 평가를 포괄적인 mutation score로 부르지 않는다.

## 에이전트 실행 규칙

- 소스와 기존 테스트를 탐색하고 위 시나리오 ID를 근거로 검증 계획을 작성한다.
- 테스트 파일 생성 후 실제 Gradle 명령을 실행하고 XML 결과를 읽는다.
- 컴파일/환경/검증 실패를 분리한다. 실패를 없애려고 구현 코드를 자동 변경하지 않는다.
- 테스트 수정 재시도는 최대 2회로 제한하고, 해결되지 않은 실패와 정책 질문을 보고한다.
- 보고서에 성공 여부뿐 아니라 실행 명령·종료 코드·테스트 수·실패 원인·수정 파일을 남긴다.
- 문서는 코드에서 관찰한 계약과 테스트로 검증한 동작, 미확정 정책을 구분한다.

이 문서는 구현 전 기준 명세다. 후속 에이전트 구현과 실제 검증 결과는 `../test-agent/implementation-log.md`를 참고한다. 이 명세의 계획 항목 모두가 구현된 것은 아니다.
