# 보상 테스트 에이전트 개발 기록

작성일: 2026-10-18 (Asia/Seoul)

## 해결하려는 문제

Doody는 안드로이드 화면을 통한 기능 확인을 중심으로 개발했다는 사용자 경험에서 출발했다. 저장소에는 일부 유틸리티·AI 클라이언트 테스트가 있었지만, 보상 서비스의 금액 제한·수집 중복·기본값·출처 기록을 반복 검증하는 서비스 테스트는 없었다.

목표는 보상 서비스의 코드를 조사하고 테스트를 생성·실행한 결과를 모델에 돌려주는 루프를 만드는 것이다. 기존 구현을 정답이라고 무조건 복제하지 않도록 관찰한 동작과 미확정 정책을 명세에서 구분했다.

## 실제 구현

- Node.js 표준 라이브러리로 도구 실행기, 상태 저장, 요청/응답 이력, Markdown 보고서 구현.
- 읽기 도구와 고정된 테스트 파일 쓰기 도구 제공. 서비스 구현 변경 도구는 제공하지 않음.
- Gradle 종료 코드와 JUnit XML을 함께 사용해 실행 결과 분류.
- 반복 횟수 제한과 이전 결과 무효화, 테스트 소스 해시 검증 추가.
- 대화 모델을 연결하는 세션 모드 및 OpenAI Responses API 어댑터 구현.
- 별도 복사본을 이용하는 결함 주입 평가 구현.

## 실제 시행착오

1. 초기 빌드는 기본 Java 17 및 DB 설정 문제를 분리해야 했다. 설치된 JDK 21과 테스트 전용 H2 설정으로 기준 빌드를 확보했다.
2. 첫 생성본의 테스트 20개는 통과했다. 그러나 중복 수집 방지 조건을 제거했을 때 테스트 대역이 null을 반환해 우연한 예외로 실패할 수 있었다. 중복 시나리오의 저장 대역도 실제 엔티티를 반환하도록 구성해, 결함을 중복 허용에 대한 단언 실패로 확인하도록 개선했다.
3. 결함 평가 중 XML 파서가 self-closing 성공 testcase와 다음 실패 testcase를 묶어 실패 이름을 잘못 표시하는 문제를 발견했다. 파서를 수정하고 선행 성공 항목이 있는 회귀 사례를 추가했다.
4. Mockito의 `NoInteractionsWanted` 검증 실패가 처음 평가 집계에서는 탐지로 인정되지 않았다. 실제 실패를 확인하고 분류를 수정한 뒤 이미 생성된 XML을 재집계했다. 이 변경은 실패한 테스트를 통과시킨 것이 아니라 결과 집계 오류를 수정한 것이다.

## 결과와 증거

최종 측정값은 같은 폴더의 `verification-results.json`과 `evaluation-results.json`에 보존한다. 모델이 설명한 숫자보다 실제 실행 결과를 우선한다. 세부 로그와 원본 XML은 `.agent-runs/reward-demo/` 및 `.agent-runs/reward-evaluation/`에 있다.

선택한 결함은 금액 제한 제거, 중복 수집 방지 제거, 잘못된 기본 등급, 포인트 출처 ID 누락, 연락처 축 변경이다. 이 5개를 탐지했다는 결과를 일반적인 100% 탐지율이나 실제 운영 버그 5개 발견으로 표현하지 않는다.

## 아직 검증하지 않은 것

- 실제 OpenAI API를 통한 무인 실행 및 모델의 실패 후 자동 수정.
- 실제 PostgreSQL에서의 DB 제약·동시성·트랜잭션 검증.
- AWS, 안드로이드, 실제 AI 서버와의 통합.
- 사용자 수, 시간 절감, 운영 장애 감소 등 실사용 성과.

## API 문서화 확장

후속으로 두디 잡기 API의 MockMvc 계약 테스트 4개와 `write_api_doc` 도구를 추가했다. 보상 테스트 20개와 HTTP 테스트 4개가 통과한 뒤, 모델이 관련 Controller·Service·DTO·응답/예외 처리 소스를 읽고 Markdown 명세를 생성했다. 전체 Java 테스트는 35개, 실행기·어댑터 테스트는 7개가 통과했다.

기존 Notion API 명세서는 사용자가 개발 당시 개발자가 직접 작성한 문서라고 설명했다. 공개 페이지에서 기능·HTTP 메서드·경로·완료 상태와 별도 AI 엔드포인트 목록을 확인했다. 과거 수동 작업 시간은 기록이 없어 단축률을 산출하지 않았다. 문서 생성 직전 테스트 실행만 약 15.4초로 측정됐으며 전체 개발·작성 시간과 구분한다.

이번 구현과 테스트는 Codex의 도움을 받아 작성했다. 본인의 자소서에는 직접 이해·확인하고 설명할 수 있는 설계 결정과 검증 과정을 중심으로 기록한다. 현재 실행은 대화 모델이 도구를 선택하고 CLI가 실행한 방식이라는 점을 유지한다.

## 면접 전에 직접 설명할 항목

- 단순 테스트 코드 생성과 실행 결과를 다시 받는 에이전트 루프는 어떻게 다른가?
- 테스트 통과만으로 테스트 품질을 판단할 수 없는 이유는 무엇인가?
- 저장 호출 횟수와 저장 객체 필드를 각각 왜 검증했는가?
- 중복 수집 검증에서 mock의 null 반환을 왜 보완했는가?
- 코드에서 읽은 현재 동작과 제품이 의도한 정책은 어떻게 구분했는가?
- 선택한 결함 5종의 평가가 보장하지 않는 것은 무엇인가?
